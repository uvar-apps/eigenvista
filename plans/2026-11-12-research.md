# Research findings: compatibility, memory and maintenance

Date: 12 November 2026 (Australia/Perth). Baseline: merged main `06ecbb9`,
EigenVista 0.5.12. Selected issues: #46, #39, #37, #38 and #35. All eleven open
`needs-research` issues were considered; the [index](README.md) records why the
other six were deferred. This is a focused investigation, not a whole-codebase
audit or implementation of these features.

All experiments used repository-local ignored temporary storage. The original
untracked review, private chat exports, existing frozen fixtures and Molekel
checkout were preserved. Historical Rust encoder source was read from Molekel
and built only inside EigenVista's ignored research directory. No legacy C++
code was built or introduced. No application/dependency/lockfile changes,
production upgrade, new release, branch, commit or push occurred.

## #46: bounded maintenance, not an exploitation claim

`app/package.json:38` permits Vite `^7.3.0`; the current lock and installation
contain 7.3.6. A fresh read-only audit reports five advisories through that
development dependency. The wrapper binds development serving to 127.0.0.1
(`tools/run.mjs:49`), uses the standard React/SPA configuration
(`app/vite.config.ts:4`), and Tauri production loads `../dist`
(`app/src-tauri/tauri.conf.json:10`).

The publishers describe Windows or WSL/editor prerequisites for the three
editor advisories. Those prerequisites are absent in the exercised macOS/Linux
workflows. The custom HTML middleware advisory explicitly excludes the default
SPA request path; this app supplies no custom HTML middleware. React can inject
inline refresh code, so absence of inline scripts is not the exclusion. The
non-Windows imported-path collision condition was not observed. Host filesystem
contents and exploit paths were not probed. Loopback is not blanket immunity,
and source analysis is not proof that every developer environment is safe.

The [official 7.3.8 changelog](https://github.com/vitejs/vite/blob/v7.3.8/packages/vite/CHANGELOG.md)
adds one virtual-module escaping correction after 7.3.7's security backports.
Isolated manifest/lock resolutions for both 7.3.7 and 7.3.8 changed only Vite's
package version/integrity and the root declaration metadata; other package
entries were unchanged. Both candidate-lock audits reported zero advisories.
The actual app manifest/lock hashes and installed 7.3.6 remained unchanged.

Recommend raising the existing declaration floor to `^7.3.8` and locking the
tested 7.3.8 resolution, with no broad audit fix, Vite 8, or unrelated updates.
The [implementation plan](001-vite-maintenance.md) requires clean install,
production/native/browser/packaging verification and actual hosted checks.

Publisher advisory sources:
[editor path](https://github.com/vitejs/launch-editor/security/advisories/GHSA-587h-7wmj-h5pm),
[editor flags](https://github.com/vitejs/launch-editor/security/advisories/GHSA-r825-w8mm-5pxw),
[Windows escaping](https://github.com/advisories/GHSA-698v-4r3x-3vcv),
[imported-path access](https://github.com/vitejs/vite/security/advisories/GHSA-rq7h-c2jc-7f22),
[custom middleware](https://github.com/vitejs/vite/security/advisories/GHSA-9jrq-w75r-8gcw).

## #39: genuine historical producer and encode baseline

The current legacy test calls today's encoder and relabels its output
(`crates/eigenvista-format/tests/legacy_compatibility.rs:18`). That tests profile
matching, not the layout of a real older encoder. The newer preflight manifest
hash test is useful but covers only one current-profile scientific document.

For this investigation, the unmodified Rust core/format crates from Molekel tag
`v0.3.2`, original commit `24d270e4589642f741ab438d6850f56a768cb66c`, were exported
to a temporary workspace. Only workspace membership was trimmed and a fixture
driver added; original library source was unchanged. Rust 1.99.0 rebuilt the
producer. Its selected dependency versions/checksums match the historical lock;
unused workspace packages were pruned in the temporary lock. This is a
reconstructed older producer, not a file claimed to have been saved in 2026's
original release build environment.

The old encoder produced a real `molekel` / `[0,1]` /
`molekel-preview-polynomial-v1` archive containing two orbitals, one density,
one authoritative 16³ grid and three signed meshes. Its 36 array entries and
manifest digests were verified. Current actual WASM decode accepted it; science,
metadata and source associations survived documented atom-row/column
normalization. Current Save/reopen also preserved that semantic document.
This semantic comparison is not a new guarantee of identical ZIP bytes or
signed-zero bit comparisons. Future frozen-entry tests must pin numeric bytes.

- Old archive: 29,673 bytes; SHA-256
  `d82999469208e83662b8aec951e68a8307823f00556cfbc513a0760abafdfee7`.
- Current resave: 28,535 bytes; SHA-256
  `58d00394b65a89bcc07e5da90483f19feb49484cd9f9260c643bba70fa28dbd7`.
- Old manifest: 8,327 bytes. These compression hashes identify artifacts only;
  manifest/decompressed entry semantics are the compatibility contract.

A separate current native 128³ hydrogen grid (2,097,152 f64 samples) measured
three isolated optimized processes on Apple M4/macOS 27.0/Rust 1.99.0:
encode 263.979/254.696/254.919 ms, maximum RSS
182,321,152/182,304,768/182,304,768 bytes. Its archive is 9,822,901 bytes with
16,781,166 total uncompressed bytes, 14 arrays and a 3,610-byte manifest.
Sampling and file writing are outside the encode timer; RSS includes the whole
process. This is native encode evidence, not browser/WASM peak memory or an OOM
guarantee. The generic preflight still expands numeric serde values
(`crates/eigenvista-format/src/lib.rs:214–233`).

Freeze small authentic old/current examples before typed encoding or #47 layout
work. Preserve explicit f64/u32 types, shapes, entry coverage, hashes, row and
column references, empty arrays, negative zero, and nonuniform basis rows.
Keep source hashes, current profile and shared budgets. A typed writer should
not silently introduce f32 world coordinates or a new hashing algorithm.
The existing native/browser distinction remains: native numeric entries retain
signed-zero bits; browser JSON Save folds -0 to +0 and source hashes canonicalize
zero signs. Freeze native bit expectations separately from browser canonical
semantics, as documented in docs/preview-format.md:98.

## #37: exact indexing is useful, with separate limits

The pinned extractor emits triangle corners; core preflight rejects more than
2,000,000 raw corners before extraction (`compute.rs:394–453`). World positions
and transformed normals are f64 (`model.rs:61`, `compute.rs:507–524`), while the
viewport constructs f32 drawing attributes (`Viewport.tsx:390–399`).

Exact keys included every f64 position and normal bit, per surface. No position
quantization, normal averaging, triangle reordering or cross-surface merge was
used. All eight original/indexed archives passed actual WASM decoding; expanded
triangle attributes were bit-identical and other scientific metadata unchanged.

| Actual generated geometry | Original / unique tuples | Native numeric arrays before / after | Whole ZIP before / after |
| --- | --- | --- | --- |
| 31 retained water meshes, 64³ fields | 88,020 / 18,874 | 4,577,040 / 1,258,032 B | 1,968,219 / 1,632,296 B |
| Hydrogen bonding orbital, 128³ | 85,236 / 14,940 | 4,432,272 / 1,058,064 B | 552,772 / 269,699 B |

Water geometry is 72.5% smaller; its whole compressed file is only 17.1% smaller.
Three isolated processes per variant (five encodes per process) measured water
encoding 88.224→53.361 ms and hydrogen 65.926→24.282 ms, using medians of process
medians. Process RSS also fell in those encoder runs. These measurements start
after offline compaction: they do not establish lower extraction peak or total
generation latency. A compaction map can increase extraction peak.

Two concrete safeguards emerged:

- A valid 17³ sphere grid at origin `[1e8;3]`, spacing 1e-3, produced 534 distinct
  f64 positions; converting world positions to f32 collapsed all 534 to one.
  Preserve durable f64 data. This does not claim the current f32 renderer can
  display those extreme coordinates accurately.
- Position-only sharing merges different normal bits: 4,002 of 14,872 water
  positions had multiple normal tuples. Preserve normals and all future vertex
  attributes in the key.

Custom shaders create a separate compatibility choice: remapping indices changes
`gl_VertexID`, even when triangle attributes are identical. The current shader
loader does not prohibit that built-in. Recommend keeping old loaded arrays
untouched and preserving raw vertex order and original indices for custom
shaders on new compacted output, including reflected-grid winding swaps, or
explicitly agreeing a different regeneration contract. Merely deindexing in
triangle draw order is insufficient to preserve those original vertex IDs.
Do not claim arbitrary shader pixel identity until that policy is tested.

Use the existing format's general indices and f64 storage first. Do not raise
raw extraction limits from compact final size; keep raw-corner, unique-vertex
and index bounds distinct. Replacing the extractor with an edge-identity API
and narrowing precision are separate projects.
Primary references: [mcubes 0.1.7](https://docs.rs/mcubes/0.1.7/src/mcubes/lib.rs.html),
[Three geometry](https://threejs.org/docs/pages/BufferGeometry.html),
[GLSL ES specification](https://registry.khronos.org/OpenGL/specs/es/3.0/GLSL_ES_Specification_3.00.pdf).

## #38: isolate transfer benefit from the full pipeline

Current generated surfaces leave WASM as JSON, are parsed in the worker and
structured-cloned as number arrays (`science.worker.ts:72–104`). Display grids
already use transferable typed buffers. The main Document still uses number[];
putting typed arrays directly into it would change JSON serialization and Save.

The same real 128³ hydrogen surface (85,236 corners, 10.57 MB Document JSON)
was sent through real workers in Chromium 153.0.8010.12 and WebKit 26.6, five fresh workers per
mode/engine. Typed mode created owned Float64/Uint32 buffers, transferred them,
then restored plain Document arrays with Array.from. Both paths used the actual
installed Three geometry constructors. All 20 samples preserved geometry and
metadata SHA-256 and verified sender detachment for all transferred buffers.

| Engine | Clone phase median | Typed phase median |
| --- | --- | --- |
| Chromium | 15.4 ms | 7.8 ms |
| WebKit | 12 ms | 6 ms |

These combine request-to-payload, plain-array restoration and CPU staging only.
Common JSON parsing (~9–10 ms), worker startup, WASM, publication, Save and GPU
upload are excluded. Array.from still costs ~5–7 ms. A separate current Node/WASM
run measured initial sampling 93.780 ms, warm meshing-plus-JSON about 45 ms and
JSON parsing about 13 ms for that one field; those phases are not separated
further and must not be added as a browser end-to-end benchmark.

No browser peak-memory conclusion is supported. Chromium offered a coarse main
heap indicator (17.1 MB clone / 27.6 MB typed), and WebKit none. These are not
full live worker/main/backing-store peaks. Node process RSS is not browser RSS.
The prototype still begins with JSON and does not implement a typed Rust API.

Prefer a narrow mesh-output packet after indexing, retaining f64 authoritative
data and the current Document adapter initially. Use JS-owned buffers copied
from WASM, transfer only at completed response publication, dispose partial
packets on error, and discard detached/stale buffers after cancellation/restart.
[wasm-bindgen numeric returns copy to JS typed arrays](https://wasm-bindgen.github.io/wasm-bindgen/reference/types/boxed-number-slices.html);
[transfer ownership detaches sender buffers](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Transferable_objects).
This is not a zero-copy whole pipeline. Remeasure after compaction before
committing to a broad transport/model rewrite.

## #35: capacity must fit import and persistence together

Both importer and core cap total MOs at 512; the importer separately allows
1,024 AOs and 500,000 input lines. Dense and sparse 300-AO/600-MO inputs
reproduced the MO-513 rejection. Dense 512-AO/1,024-MO input instead hit line
500,001. The [official PySCF writer](https://pyscf.org/_modules/pyscf/tools/molden.html#dump_scf)
emits AO rows for each MO and both UHF spin sets. Sparse synthetic files can
hide this independent guard.

Complete two-spin coefficients plus four dense f64 matrices require 48*n² bytes:

| AOs / complete MOs | Numeric payload before other data |
| --- | --- |
| 300 / 600 | 4,320,000 B (4.12 MiB) |
| 512 / 1,024 | 12 MiB |
| 1,024 / 2,048 | 48 MiB |
| 2,048 / 4,096 | 192 MiB |
| 4,096 / 8,192 | 768 MiB |

The last two exceed today's 128 MiB uncompressed profile without a grid, mesh,
basis or manifest. Raising an orbital constant cannot solve this.

Current-cap, synthetic 1,024-AO/400-MO UHF data measured three isolated native
processes per operation: import median 115.4 ms / ~62.1 MB RSS; Document JSON
102.3 MB / ~165.2 MB RSS; encode 921.2 ms / ~437.7 MB RSS. Exact native roundtrip
passed and its process reached ~520.7 MB RSS. Inputs are valid for the import
profile but not converged physical wavefunctions. These are native operation
measurements, not browser/OOM guarantees or timings for a complete 1,024-AO set.

The current 125-AO/118-MO user workload is not blocked. Keep present limits while
qualifying a real larger workload. A targeted 300/600 complete-set qualification
is plausible within current raw persistence bytes, but needs actual WASM
import/save/reopen and finite memory budgets. Separate arbitrary supplied
matrices from any future lazy/factorized occupation-density representation.
